# MyPetStore 实验一版本规划

建议将实验一拆为 **10 个里程碑版本：v0.1.0 至 v0.9.0，以及正式交付版 v1.0.0**。完成全部必做项后，再按时间选择 v1.1.0 扩展。版本数量是本项目的实施建议，不是课程额外规定；它将 PRD 第 12 章的六个开发阶段细分为适合演示、检查和 Git 提交的成果。

本文件仅规划后续开发，不表示表中功能已实现或验收已通过。当前代码基础对应 v0.1.0 候选版本，不能称为完整商城。

## 1 依据与范围

- 《软件开发架构平台》实验指导书2025级 实验一：用户端与后台管理系统、Git 同步、实验报告及成员分工要求。
- 《MyPetStore 项目需求规约 PRD》V1.1 学生实施基线，2026 年 11 月 9 日：第 3 章范围、第 6—10 章业务及技术要求、第 11 章验收、第 12 章阶段、第 14 章统一规则、第 15 章提交要求。
- 当前代码及已有验证：Spring Boot、数据源配置、MVC 文本接口、User/Mapper/Service/DTO、用户 JSON 与 Thymeleaf 演示、3 项 Service 单元测试，以及真实 Git 提交记录。

### 需要向老师确认的材料差异

指导书较概括，提到注册、验证码、后台改密、商品和订单修改删除；PRD 的详细实施基线明确排除注册与验证码，商品下架代替删除，订单保留且只能按状态机操作，后台用户管理列为 P1 且不开放任意改密。本计划先按较新 PRD 的具体业务规则安排，不将两份材料简单叠加。最终评分范围应向老师确认；确认前不擅自实现订单删除、任意状态编辑或密码重置。

PRD 内部也有概述与细则不一致：第 3.3 节的排除项包含价格/新品排序切换，而第 6.3 节、第 13—14 章明确要求四种商品排序。本计划按后面的详细统一规则保留四种排序，并将此差异列入确认清单。独立下单请求幂等标识按第 3 章暂不安排；“同一购物车不能重复成交”始终是 P0，不能因此省略。

PRD 引用了指导书 V01—V18，但本次提供的旧版 .doc 中没有对应编号表；需要核对老师配套验收清单。这里先按 PRD 的 AC-01—AC-32 追踪全部 P0，AC-33、AC-34 为选做。**V01—V18 是引用的验收编号，不是要求开发十八个软件版本。**

## 2 所有版本共同遵守的设计

1. 两个独立 Spring Boot 工程：用户端 `MyPetStore-SSM`，管理端 `MyPetStore-admin`；都使用 Spring MVC、Thymeleaf、MyBatis-Plus，共用 `MyPetStore` 的七张业务表。管理端需要单独可构建运行，不能只是在用户端增加几个后台 Controller。
2. 用户端端口 8080、Cookie `PETSTORE_USER_SESSION`；管理端端口 8081、Cookie `PETSTORE_ADMIN_SESSION`。Session 各自独立，不通过 HTTP 相互调用购买或补货业务。
3. Controller 处理请求和视图，Service 实现业务与事务，Mapper 访问数据。Service 不依赖 HTTP、Model 或 Session 对象；当前用户身份由服务端取得，写操作检查角色、状态、归属和 CSRF。
4. 购物车存数据库，Session 只保存最小登录身份和临时结算确认；业务金额使用 BigDecimal，数据库价格及成交快照为可信来源。
5. 下单时扣库存，模拟支付不再扣库存；待支付取消恢复一次。事务、并发、归属、版本冲突从相关功能的首个版本开始实现，v0.9.0 再集中回归，不能拖到最后补救。
6. 使用提供的站内资源，不做真实支付、物流轨迹、注册、验证码、多规格、优惠券、推荐算法或微服务。P0 完成前不扩展业务。
7. 数据库手动初始化，`01-schema.sql` 与 `02-schema-with-demo.sql` 二选一，不在应用启动时重建或清库。测试数据按需备份或恢复，故障注入只存在测试环境。

## 4 可选版本与后续实验

**v1.1.0 为可选增强版，不是实验一 P0 的前置条件。** 全部 P0 通过后，可按时间单独选择本人资料及修改密码、确认收货、后台普通用户启停或站内相册维护。选做的功能必须完整测试，未做的功能隐藏入口；对应 AC-33、AC-34 和 FR-A-07。

**实验二另立 v2.x 计划。** REST API、Vue/React 管理端及小程序属于后续范围；本次不把它们和实验一服务器端渲染版本混在一起，也不直接把浏览器 Session 当作小程序身份方案。

## 5 仓库与版本记录

当前仓库根目录就是用户端项目。引入管理端的 v0.3.0 中，再安排一次保留历史的目录整理，建议形成：

```text
仓库根目录/
  MyPetStore-SSM/       用户端独立 Maven 工程
  MyPetStore-admin/     管理端独立 Maven 工程
  database/            唯一来源的课程共享 SQL 与初始化说明
  docs/                版本计划、验收记录与报告材料
  README.md            双端整体运行说明
```

这是后续目录方案，本次不移动源码。两个工程不要求引入 Maven 多模块或公共 JAR。整理时让 SQL 只有一个维护来源，不复制出两份互相冲突的表结构。

- 每完成一个能说明目的的小步骤就提交并推送，不必等整个里程碑结束；例如 v0.2.0 可以依次提交“实现首页真实商品展示”“实现分类列表查询”“实现商品详情与边界处理”。
- 每个里程碑全部完成并验证后才打相应版本标签，例如 `v0.2.0`。修复该版问题可用 `v0.2.1`。本文件不预先创建标签，不补造历史提交。
- 提交说明、代码、README 和验证结果保持一致。每版记录对应需求编号、变更内容、验证方法、实际结果、证据位置及已知未完成项。
- 真实密码、令牌、本地开发配置、IDEA 私有配置、编译产物及安装包不上传。开发配置提供无密码示例。

## 6 每版共同完成标准

1. 本版功能可通过真实请求或页面验证，且有异常、空数据、非法输入及权限边界验证；只靠静态页面或成功弹窗不算完成。
2. 执行与本轮改动相关的编译和测试，说明验证边界。单元测试不冒充数据库/事务/浏览器验证，连续点击不冒充独立事务并发。
3. 涉及下单或取消时记录订单、明细、库存、版本和购物车的前后结果；事务失败测试不能被外层测试事务掩盖。
4. 涉及两端联动时使用两个实际应用。两端共享数据库，但每项业务使用各自完整的数据库事务，不能靠单个 Java 进程锁协调。
5. 版本说明及实际验证记录已提交并推送，老师能找到对应提交；只有全部里程碑条件满足时才创建版本标签。

实验一版本中持续整理报告素材和成员分工，v1.0.0 完成实验一报告部分；正式报告按指导书要求与实验二报告一起提交，具体节点以老师通知为准。

计划不虚设日历截止时间：实际进度以老师发布的提交期限为准。时间不足时先完成全部 P0 并验收，压缩或取消 P1 扩展，不能削减事务、权限或数据一致性要求。
